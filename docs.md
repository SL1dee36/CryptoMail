## Аннотация

Настоящий документ представляет собой исчерпывающее научно-техническое описание архитектуры, программных интерфейсов (API) и криптографических механизмов, реализованных в защищенном почтовом комплексе **CryptoMail**.

В программном комплексе реализована гибридная криптографическая модель, объединяющая стандарты криптографической защиты информации Российской Федерации (ГОСТ Р 34.12-2015 «Кузнечик», ГОСТ Р 34.11-2012 «Стрибог») и сверхдлинные асимметричные криптосистемы на базе алгоритма RSA с длиной ключа до 32768 бит (RSA-32K). Безопасность функционирования обеспечивается трехфакторной аутентификацией (3FA), электронной цифровой подписью (ЭЦП), контролем целостности сообщений на базе имитовставки HMAC и прозрачным криптографическим экранированием базы данных на уровне хранения (Encryption at Rest).

# Глава 1. Архитектура программного комплекса и спецификация API

## 1.1. Архитектурная модель системы

Программный комплекс CryptoMail спроектирован по многоуровневой модульной архитектуре, гарантирующей строгое разграничение зоны бизнес-логики, криптографического ядра и интерфейса хранения данных:

1. **Презентационный уровень (Presentation Layer)**:
   * Реализован на базе асинхронного веб-фреймворка FastAPI и шаблонизатора Jinja2.
   * Клиентский интерфейс выполнен в соответствии со спецификацией Material Design 3 Expressive, поддерживая динамический отклик, реактивные индикаторы прогресса вычислений и переключение цветовых схем.
2. **Сервисный уровень (Service & Business Logic Layer)**:
   * `auth_service`: управление жизненным циклом пользователей, многофакторная аутентификация (3FA), генерация и проверка одноразовых паролей (OTP) и резервных кодов восстановления.
   * `message_service`: оркестрация процессов формирования конвертов, подписания дайджестов и маршрутизации защищенных сообщений.
   * `crypto_task_service`: диспетчер фоновых асинхронных потоков для ресурсоемких криптографических операций (RSA-32K) с фиксацией промежуточных метрик скорости и прогресса.
   * `export_service`: защищенная выгрузка журналов переписки в форматах JSON и PDF с поддержкой шрифтового кодирования кириллицы.
   * `mail_server`: встроенный асинхронный почтовый демон протокола RFC 5321 (SMTP), функционирующий на `127.0.0.1:1025`.
3. **Криптографическое ядро (Cryptographic Core Layer, пакет `crypto`)**:
   * Независимый вычислительный слой, не содержащий зависимостей от веб-уровня и реализующий алгоритмы ГОСТ Р 34.12-2015, ГОСТ Р 34.11-2012, ГОСТ Р 34.10-2012 и RSA-OAEP.
4. **Уровень хранения данных (Data Storage Layer)**:
   * Реализован посредством объектно-реляционного отображения (ORM SQLAlchemy 2.0).
   * База данных SQLite/PostgreSQL с принудительным симметричным шифрованием критических полей шифром «Кузнечик».

## 1.2. Протокол трехфакторной аутентификации (3FA) и ролевая модель (RBAC)

Аутентификация субъекта строится на последовательном подтверждении трех независимых факторов:

$$\text{Auth} = F_1(\text{Знание}) \land F_2(\text{Владение каналом связи}) \land F_3(\text{Владение криптографическим токеном})$$

1. **Фактор 1 (Знание)**: Парольная фраза пользователя, проверяемая по схеме PBKDF2 на базе ГОСТ Р 34.11-2012 «Стрибог-512» (1000 итераций со случайной 16-байтовой солью).
2. **Фактор 2 (Владение почтовым ящиком)**: Генерация псевдослучайного 6-значного одноразового кода (OTP), доставляемого через локальный SMTP-сервер на зарегистрированный адрес электронной почты. Срок жизни сессии $T_{\text{lifetime}} = 300$ с.
3. **Фактор 3 (Владение генератором TOTP или аварийным ключом)**:
   * Проверка динамического кода TOTP (RFC 6238) с шагом времени $T_X = 30$ с и алгоритмом HMAC-SHA1.
   * Альтернативный путь: использование одного из одноразовых криптографических резервных кодов восстановления (Recovery Codes), хранящихся в базе данных в зашифрованном виде и аннулируемых сразу после применения.

### Ролевая модель разграничения доступа (RBAC)
* **Гость (`guest`)**: Доступ исключительно в режиме чтения общедоступных параметров. Отправка сообщений и модификация криптографических параметров заблокированы.
* **Пользователь (`user`)**: Полноправный обмен сообщениями, перевыпуск личных ключей RSA и ЭЦП, управление личным архивом, экспорт переписки.
* **Администратор (`admin`)**: Аудит системы, глобальный экспорт дешифрованных и зашифрованных сообщений, сброс паролей пользователей, переназначение ролей.

## 1.3. Спецификация программного интерфейса (REST API v1)

CryptoMail предоставляет документированный интерфейс прикладного программирования для взаимодействия внешних систем, утилит командной строки (CLI) и автоматизированных сервисов.

### 1. Генерация ключевой пары RSA
* **URL**: `POST /api/v1/crypto/rsa/generate`
* **Формат запроса**:
  ```json
  {
    "bits": 4096
  }
  ```
* **Формат ответа**:
  ```json
  {
    "bits": 4096,
    "private_key_pem": "-----BEGIN PRIVATE KEY-----\n...",
    "public_key_pem": "-----BEGIN PUBLIC KEY-----\n..."
  }
  ```

### 2. Гибридное шифрование RSA
* **URL**: `POST /api/v1/crypto/rsa/encrypt`
* **Формат запроса**:
  ```json
  {
    "public_key_pem": "-----BEGIN PUBLIC KEY-----\n...",
    "data": "Конфиденциальное сообщение"
  }
  ```
* **Формат ответа**:
  ```json
  {
    "encrypted_bundle": "{\"alg\": \"RSA-HYBRID\", \"key_bits\": 4096, \"enc_key\": \"...\", \"iv\": \"...\", \"ciphertext\": \"...\"}"
  }
  ```

### 3. Расшифрование гибридного бандла RSA
* **URL**: `POST /api/v1/crypto/rsa/decrypt`
* **Формат запроса**:
  ```json
  {
    "private_key_pem": "-----BEGIN PRIVATE KEY-----\n...",
    "bundle_json": "{\"alg\": \"RSA-HYBRID\", ...}"
  }
  ```
* **Формат ответа**:
  ```json
  {
    "decrypted_data": "Конфиденциальное сообщение"
  }
  ```

### 4. Симметричное шифрование ГОСТ «Кузнечик»
* **URL**: `POST /api/v1/crypto/kuznyechik/encrypt`
* **Параметры**:
  * `key_hex` (string, 64 hex-символа): 256-битный ключ.
  * `data` (string): данные открытого текста.
  * `mode` (string): режим шифрования (`"cbc"` или `"ctr"`).
* **Формат ответа**:
  ```json
  {
    "ciphertext_base64": "...",
    "mode": "cbc"
  }
  ```

### 5. Симметричное расшифрование ГОСТ «Кузнечик»
* **URL**: `POST /api/v1/crypto/kuznyechik/decrypt`
* **Параметры**: аналогичны запросу шифрования с передачей шифротекста в поле `data` в кодировке Base64.
* **Формат ответа**:
  ```json
  {
    "decrypted_data": "...",
    "mode": "cbc"
  }
  ```

### 6. Вычисление хеш-кода и имитовставки ГОСТ «Стрибог»
* **URL**: `POST /api/v1/crypto/streebog/hash`
* **Параметры**:
  * `data` (string): входное сообщение.
  * `bits` (int): 256 или 512 (по умолчанию 512).
  * `key` (string, опционально): ключ для вычисления HMAC.
* **Формат ответа**:
  ```json
  {
    "hash_streebog512": "486f64c1917879417fef082b3381a4e2...",
    "hmac_streebog512": "..."
  }
  ```

### 7. Формирование и проверка ЭЦП
* **Подписание**: `POST /api/v1/crypto/ecp/sign`
  * Вход: `private_key_pem`, `data`.
  * Выход: `{"signature_b64": "...", "digest_algorithm": "GOST R 34.11-2012 Streebog-512"}`.
* **Верификация**: `POST /api/v1/crypto/ecp/verify`
  * Вход: `public_key_pem`, `data`, `signature_b64`.
  * Выход: `{"is_valid": true}`.

## 1.4. Фоновый асинхронный трекер задач (Crypto Task Tracker)

Операции криптографического преобразования над экстремальными ключами (RSA-32768) требуют значительного времени работы центрального процессора (от десятков секунд до нескольких минут). Для предотвращения блокировки сетевого цикла событий (Event Loop) реализована модель отложенных задач:

* `POST /api/crypto/encrypt_task` — постановка задачи шифрования сообщения в очередь потоков с возвратом уникального идентификатора `task_id`.
* `POST /api/crypto/decrypt_task/{message_id}` — постановка задачи дешифрования.
* `GET /api/crypto/tasks/{task_id}` — опрос состояния вычислительного процесса.

Структура объекта состояния задачи:

# Глава 2. Математические основы асимметричной криптосистемы RSA и RSA-32768

## 2.1. Теоретико-числовой базис

Стойкость асимметричной криптосистемы RSA опирается на вычислительную сложность задачи факторизации больших составных целых чисел (проблема поиска делителей в кольце целых чисел $\mathbb{Z}$).

Пусть $p$ и $q$ — два различных больших простых числа:

$$n = p \cdot q$$

Значение $n$ называется модулем системы. Функция Эйлера $\varphi(n)$ определяет порядок мультипликативной группы кольца вычетов $\mathbb{Z}_n^*$:

$$\varphi(n) = (p - 1)(q - 1)$$

Открытая экспонента $e$ выбирается взаимно простой с $\varphi(n)$:

$$\gcd(e, \varphi(n)) = 1$$

В системе CryptoMail в качестве $e$ фиксировано значение Ферма $F_4 = 2^{16} + 1 = 65537$. Данное число обладает весом Хэмминга равным 2 (в двоичном представлении: $10000000000000001_2$), что минимизирует количество операций умножения при возведении в степень по алгоритму «square-and-multiply» (ровно 16 возведений в квадрат и 1 умножение).

Секретная экспонента $d$ вычисляется как мультипликативное обратное к $e$ по модулю $\varphi(n)$ с помощью расширенного алгоритма Евклида:

$$e \cdot d \equiv 1 \pmod{\varphi(n)} \iff d \equiv e^{-1} \pmod{\varphi(n)}$$

На основании теоремы Эйлера, для любого сообщения $m \in \mathbb{Z}_n^*$:

$$c = m^e \bmod n \implies m' = c^d \equiv (m^e)^d \equiv m^{1 + k\varphi(n)} \equiv m \cdot (m^{\varphi(n)})^k \equiv m \cdot 1^k \equiv m \pmod n$$

## 2.2. Генерация экстремальных простых чисел и параллельное тестирование простоты

В контексте RSA-32768 длина модуля составляет ровно $k = 32768$ бит, следовательно, длины сомножителей $p$ и $q$ равны:

$$\ell = \frac{k}{2} = 16384 \text{ бит}$$

Десятичный порядок каждого сомножителя превышает 4930 знаков. Генерация подобных величин детерминированными методами (например, доказательством простоты Поклингтона или ECPP) практически нереализуема в приемлемое время. В комплексе CryptoMail применен оптимизированный двухэтапный вероятностный конвейер.

### 1. Этап решета малых простых чисел (Pre-sieve filtering)
Кандидат $cand$ формируется генератором криптографически стойких случайных чисел `secrets.randbits(16384)` с обязательной фиксацией двух старших разрядов и младшего бита:

$$cand = r \lor (1 \ll (\ell - 1)) \lor (1 \ll (\ell - 2)) \lor 1$$

Установка двух старших битов гарантирует выполнение неравенства:

$$cand_1 \cdot cand_2 \ge \left(\frac{3}{2} \cdot 2^{\ell - 1}\right)^2 = \frac{9}{4} \cdot 2^{2\ell - 2} = 1.125 \cdot 2^{2\ell - 1} \ge 2^{2\ell - 1}$$

что математически строго исключает потерю разрядности модуля ($n = p \cdot q$ всегда имеет длину ровно $2\ell = 32768$ бит).

Кандидат проверяется на делимость без остатка по таблице первых 303 простых чисел ($P \le 2000$). Проверка отсекает более $88\%$ составных чисел с минимальными вычислительными затратами.

### 2. Вероятностный тест Миллера — Рабина
Для прошедших решето кандидатов проверяется выполнение теста Миллера — Рабина. Число $n - 1$ представляется в виде:

$$n - 1 = 2^s \cdot d, \quad d \text{ — нечетное}$$

Выбирается случайная база $a \in [2, n - 2]$. Вычисляется $x = a^d \bmod n$. Если $x = 1$ или $x = n - 1$, кандидат признается псевдопростым по базе $a$. В противном случае выполняется $s - 1$ возведений в квадрат:

$$x \leftarrow x^2 \bmod n$$

Если ни на одном шаге $x$ не обратился в $n - 1$, число гарантированно составное. При $r = 6$ независимых раундах вероятность принятия составного числа за простое (вероятность ошибки) ограничена величиной:

$$P(\text{ошибка}) \le 4^{-r} = 4^{-6} = 2^{-12} \approx 2.44 \times 10^{-4}$$

А с учетом априорной плотности распределения простых чисел порядка $2^{16384}$ реальная вероятность ложного срабатывания составляет менее $2^{-128}$, что удовлетворяет требованиям стандартов FIPS 186-4.

### 3. Многопроцессорный параллелизм
Поиск $p$ и $q$ распределяется между рабочими процессами (`multiprocessing.Process`) с общей разделяемой памятью счетчика кандидатов (`mp.Value`) и события остановки (`mp.Event`). При обнаружении простого числа первым из процессов подается сигнал завершения остальным воркерам.

## 2.3. Механизм предварительной генерации (Pregeneration Pool)

Поскольку параллельный поиск сомножителей по 16384 бит занимает от десятков секунд до нескольких минут, в системе реализован механизм предварительной генерации параметров $p$ и $q$:

1. Команда `python cli.py rsa-pregen` (или функция `generate_and_save_pq()`) вычисляет простые числа в фоновом режиме и размещает их в структурированном хранилище `data/rsa_pregen/`.
2. При вызове шифрования или выпуска ключа с флагом `--pregen` параметры считываются из хранилища мгновенно, а итоговая ключевая пара собирается за время порядка **0.02–0.05 секунды**.

## 2.4. Оптимизация дешифрования на основе Китайской теоремы об остатках (CRT)

Прямое дешифрование по формуле $m = c^d \bmod n$ для $n$ длиной 32768 бит вычислительно неэффективно: показатель степени $d$ содержит 32768 бит, требуя порядка 49152 операций умножения над сверхдлинными числами.

В соответствии с Китайской теоремой об остатках, кольцо $\mathbb{Z}_n$ изоморфно прямому произведению полей:

$$\mathbb{Z}_n \cong \mathbb{Z}_p \times \mathbb{Z}_q$$

В системе предварительно рассчитываются CRT-компоненты:

$$d_p = d \bmod (p - 1), \quad d_q = d \bmod (q - 1), \quad q_{inv} = q^{-1} \bmod p$$

Вычисление выполняется в два этапа над числами вдвое меньшей разрядности (16384 бит):

$$m_1 = c^{d_p} \bmod p, \quad m_2 = c^{d_q} \bmod q$$

Окончательное значение открытого текста собирается по схеме Гарнера (Garner's Formula):

$$h = (q_{inv} \cdot (m_1 - m_2)) \bmod p$$
$$m = m_2 + h \cdot q$$

Поскольку сложность операции умножения длины $L$ квадритична ($O(L^2)$) или сублинейна ($O(L \log L \log \log L)$), уменьшение размерности операндов вдвое снижает затраты на каждое возведение в степень в 4 раза. С учетом двух ветвей вычислений суммарное ускорение дешифрования составляет:

$$\text{Speedup}_{\text{CRT}} \approx \frac{L^3}{2 \cdot (L/2)^3} = 4$$

## 2.5. Схема дополнения RSA-OAEP (RFC 8017)

Прямое («сырое») применение RSA ($c = m^e \bmod n$) недопустимо вследствие гомоморфных свойств и уязвимости к атакам на основе подобранного шифротекста (IND-CCA).

В комплексе CryptoMail задействовано оптимальное асимметричное дополнение с рандомизацией **OAEP (Optimal Asymmetric Encryption Padding)** по стандарту RFC 8017:

```
                  +----------+       +----------+
                  |  Message |       |  Pad 0x00|
                  +----------+       +----------+
                        |                  |
                        +--------+---------+
                                 |
                                 v
     +------------+         +----------+
     | Seed (Rand)|         |    DB    |
     +------------+         +----------+
           |                      |
           |      +--------+      |
           |----->| MGF( ) |----->(+)
           |      +--------+      |
           v                      v
     +------------+         +----------+
     |    Seed    |         | MaskedDB |
     +------------+         +----------+
           |                      |
           |      +--------+      |
          (+) <---| MGF( ) |<-----|
           |      +--------+      |
           v                      |
     +------------+               |
     | MaskedSeed |               |
     +------------+               |
           |                      |
           +----------+-----------+
                      |
                      v
             EM = 0x00 || MaskedSeed || MaskedDB
```

1. Формируется блок данных $DB = \text{Hash}(L) \parallel PS \parallel 0x01 \parallel M$.
2. Генерируется случайное число $Seed$ длиной, равной длине хеша SHA-256 (32 байта).
3. Маскирующий блок: $dbMask = \text{MGF1}(Seed, \text{len}(DB))$.
4. $maskedDB = DB \oplus dbMask$.
5. $seedMask = \text{MGF1}(maskedDB, \text{len}(Seed))$.
6. $maskedSeed = Seed \oplus seedMask$.
7. Итоговое закодированное сообщение: $EM = 0x00 \parallel maskedSeed \parallel maskedDB$.

Функция MGF1 (Mask Generation Function) функционирует на базе криптографического хеша SHA-256.

---

## 2.6. Гибридная конвертная криптосистема (Hybrid Envelope Encryption)

В связи с тем, что асимметричное шифрование ограничено длиной блока $k / 8$ байт, CryptoMail использует гибридную схему:
1. Для каждого сеанса связи генерируется криптографически стойкий 256-битный симметричный сессионный ключ $K_{\text{sess}} \in_R \{0, 1\}^{256}$ и 128-битный вектор инициализации $IV \in_R \{0, 1\}^{128}$.
2. Открытый текст произвольной длины шифруется симметричным шифром ГОСТ Р 34.12-2015 «Кузнечик» в режиме CTR.
3. Сессионный ключ $K_{\text{sess}}$ шифруется открытым ключом получателя RSA-32K с набивкой OAEP:
   $$C_{\text{key}} = \text{RSA-OAEP}_{\text{Pub}}(K_{\text{sess}})$$
4. Итоговый криптографический бандл упаковывается в формат JSON и кодируется в Base64.

---

# Глава 3. Симметричный блочный шифр ГОСТ Р 34.12-2015 «Кузнечик»

## 3.1. Спецификация алгоритма

Шифр ГОСТ Р 34.12-2015 «Кузнечик» представляет собой симметричный блочный шифр на основе подстановочно-перестановочной сети (SPN — Substitution-Permutation Network).
* Длина блока: $n = 128$ бит (16 байт).
* Длина ключа: $k = 256$ бит (32 байта).
* Количество раундов: 10.

Шифрование блока $a \in V_{128}$ описывается композицией раундовых функций:

$$E_{K}(a) = X[K_{10}] \circ \prod_{i=1}^{9} \Big( L \circ S \circ X[K_i] \Big) (a)$$

где:
* $X[K](a) = a \oplus K$ — побитовое сложение с раундовым ключом;
* $S(a)$ — нелинейное подстановочное преобразование;
* $L(a)$ — линейное диффузионное преобразование.

```
       Входной блок (128 бит)
                 |
                 v
             +-------+
             | X[K1] |  (XOR с подключом 1)
             +-------+
                 |
                 v
             +-------+
             |   S   |  (16 нелинейных S-блоков Pi)
             +-------+
                 |
                 v
             +-------+
             |   L   |  (Линейное MDS-преобразование)
             +-------+
                 |
               .....  (Повторение для раундов 2..9)
                 |
                 v
             +-------+
             | X[K10]|  (Финальный XOR с подключом 10)
             +-------+
                 |
                 v
      Шифротекст блока (128 бит)
```

---

## 3.2. Нелинейное преобразование $S$ (S-блок)

Преобразование $S \colon V_{128} \to V_{128}$ реализует параллельное применение нелинейной биективной подстановки $\pi \colon V_8 \to V_8$ к каждому из 16 байт входного блока:

$$S(a) = S(a_{15} \parallel a_{14} \parallel \dots \parallel a_0) = \pi(a_{15}) \parallel \pi(a_{14}) \parallel \dots \parallel \pi(a_0)$$

Таблица $\pi$ строго определена в RFC 7801 и обладает следующими криптографическими свойствами:
* Нелинейность: $N_{\pi} = 112$ (высокая стойкость к линейному криптоанализу).
* Максимальная дифференциальная вероятность: $DP_{\max} = 8 / 256 = 2^{-5}$ (стойкость к дифференциальному криптоанализу).
* Отсутствие неподвижных точек: $\pi(x) \neq x$ для всех $x \in V_8$.

---

## 3.3. Линейное преобразование $L$ и арифметика в поле $\mathbb{F}_{2^8}$

Линейное преобразование обеспечивает лавинный эффект: изменение одного бита на входе раунда изменяет в среднем половину битов на выходе.

Преобразование $L$ основано на итеративном применении отображения сдвигового регистра $R \colon V_{128} \to V_{128}$:

$$L(a) = R^{16}(a) = \underbrace{R(R(\dots R(a)\dots))}_{16 \text{ раз}}$$

Отображение $R$ сдвигает байты блока вправо на одну позицию, а в старший байт записывает линейную комбинацию всех байтов над конечным полем $\mathbb{F}_{2^8}$:

$$R(a) = R(a_{15} \parallel a_{14} \parallel \dots \parallel a_0) = \left( \bigoplus_{i=0}^{15} c_i \cdot a_i \right) \parallel a_{15} \parallel a_{14} \parallel \dots \parallel a_1$$

Поле $\mathbb{F}_{2^8}$ строится по модулю неприводимого многочлена:

$$p(x) = x^8 + x^7 + x^6 + x + 1 \in \mathbb{F}_2[x] \quad (\text{шестнадцатеричное представление: } 0\text{x}1C3)$$

Вектор констант $c = (c_{15}, \dots, c_0)$ задан в RFC 7801:
$$c = (148, 32, 133, 16, 194, 192, 1, 251, 1, 192, 194, 16, 133, 32, 148, 1)$$

Поскольку вектор $c$ формирует порождающую матрицу кода Рида — Соломона с максимальным кодовым расстоянием (MDS-свойство), преобразование $L$ имеет максимальный дифференциальный и линейный показатель ветвления, равный 17.

---

## 3.4. Процедура развертывания ключей

Мастер-ключ $K$ длиной 256 бит разбивается на две половины по 128 бит:

$$K = K_1 \parallel K_2$$

Остальные 8 раундовых ключей $K_3, \dots, K_{10}$ вычисляются парами по схеме Фейстеля:

$$(K_{2i+1}, K_{2i+2}) = F[C_{8(i-1)+8}] \circ \dots \circ F[C_{8(i-1)+1}] (K_{2i-1}, K_{2i}), \quad i = 1, 2, 3, 4$$

Раундовая ступень Фейстеля $F[C]$ над парой $(A, B)$ с константой $C$:

$$F[C](A, B) = (L(S(A \oplus C)) \oplus B, A)$$

Константы $C_j$ вычисляются как результат применения линейного преобразования к номеру итерации: $C_j = L(\text{bin}_{128}(j))$.

---

## 3.5. Режимы функционирования шифра

1. **Режим CBC (Cipher Block Chaining, сцепление блоков)**:
   $$C_0 = IV, \quad C_i = E_K(P_i \oplus C_{i-1}), \quad i \ge 1$$
   Применяется дополнение PKCS#7: блок дополняется $pad$ байтами, каждый со значением $pad \in [1, 16]$.
2. **Режим CTR (Counter, счетчик)**:
   $$CTR_i = IV \parallel \text{counter}_i$$
   $$C_i = P_i \oplus E_K(CTR_i)$$
   Преобразует блочный шифр в синхронный поточный, исключая необходимость выравнивания длины данных и набивки.

---

# Глава 4. Криптографическая хеш-функция ГОСТ Р 34.11-2012 «Стрибог»

## 4.1. Общие принципы и конструкция Меркла — Дамгора

Функция «Стрибог» вычисляет криптографический дайджест фиксированной длины (512 бит или 256 бит) для сообщений произвольной длины. Алгоритм базируется на итеративной конструкции Меркла — Дамгора с процедурой сжатия в модифицированном режиме Миягучи — Пренеля.

```
       M (сообщение)
           |
           v
     +------------+
     | Дополнение |  (1 || 00...00)
     +------------+
           |
     +-----+-----+-----+
     | m_1 | m_2 | m_N |  (Блоки по 512 бит)
     +-----+-----+-----+
        |     |     |
 IV --->[ g ]->[ g ]->[ g ]---> h_N
         ^     ^     ^
         |     |     |
        m_1   m_2   m_N
                     |
                     +---> Финализация: g(h_N, |M|) -> g(..., \Sigma) ---> Digest
```

Инициализирующий вектор $IV$:
* Для «Стрибог-512»: $IV_{512} = 0^{512}$ (64 нулевых байта).
* Для «Стрибог-256»: $IV_{256} = 0x01^{512}$ (64 байта со значением $0x01$).

Дополнение сообщения: к исходным данным $M$ приписывается бит `1`, затем необходимое число нулей до кратности 512 битам.

---

## 4.2. Функция сжатия $g_N$ и 512-битный блочный шифр

Функция сжатия $g_N(h, m)$ принимает 512-битный вектор состояния $h$, 512-битный блок сообщения $m$ и 512-битный счетчик $N$:

$$g_N(h, m) = E_{K}(m) \oplus h \oplus m$$

где ключ $K$ внутреннего блочного шифра $E$ вырабатывается из $h$ и $N$:

$$K = L \circ P \circ S(h \oplus N)$$

Внутренний блочный шифр выполняет 12 раундов преобразований над 512-битным блоком:

$$\text{State}_{i} = L \circ P \circ S(\text{State}_{i-1}) \oplus K_i, \quad i = 1, \dots, 12$$

Компоненты раундового преобразования:
1. **$S$-преобразование**: 64 параллельных нелинейных подстановки по таблице $\pi$ (совпадает с таблицей $\pi$ шифра «Кузнечик»).
2. **$P$-преобразование (перестановка $\tau$)**: перестановка байтов вектора в соответствии с перестановкой $\tau$ (RFC 6986 раздел 6.3):
   $$\tau(i) = 8 \cdot (i \bmod 8) + \lfloor i / 8 \rfloor$$
3. **$L$-преобразование**: умножение 64-битных слов состояния на двоичную матрицу $A$ размера $64 \times 64$ над полем $\mathbb{F}_2$. В программной реализации комплексно оптимизировано с помощью 8 предвычисленных таблиц по 256 64-битных слов (`TABLE_L`).

---

## 4.3. Аутентификация сообщений: HMAC-Стрибог-512 (RFC 2104)

Механизм HMAC гарантирует целостность и подтверждение подлинности источника данных с использованием общего секретного ключа $K$:

$$\text{HMAC}(K, M) = \text{Streebog512}\Big((K \oplus opad) \parallel \text{Streebog512}((K \oplus ipad) \parallel M)\Big)$$

Константы дополнения:
* $ipad = 0x36^{64}$ (внутреннее заполнение, 64 байта);
* $opad = 0x5C^{64}$ (внешнее заполнение, 64 байта).

---

## 4.4. Формирование производных ключей: PBKDF2-Стрибог-512 (RFC 8018)

Для защиты паролей от атак перебором по радужным таблицам CryptoMail использует функцию формирования ключа PBKDF2 (Password-Based Key Derivation Function 2) со Стрибог-512 в качестве псевдослучайной функции (PRF):

$$DK = \text{PBKDF2}(P, S, c, dkLen) = T_1 \parallel T_2 \parallel \dots \parallel T_l$$

$$T_i = F(P, S, c, i) = U_1 \oplus U_2 \oplus \dots \oplus U_c$$

где:
$$U_1 = \text{HMAC-Streebog512}(P, S \parallel \text{INT}_{32}(i))$$
$$U_j = \text{HMAC-Streebog512}(P, U_{j-1}), \quad j = 2, \dots, c$$

Количество итераций в системе: $c = 1000$, размер вырабатываемой соли: 16 байт ($128$ бит).

---

# Глава 5. Электронная цифровая подпись (ЭЦП) и сертификаты

## 5.1. Математические основы стандарта ГОСТ Р 34.10-2012

Электронная цифровая подпись в CryptoMail построена в строгом соответствии с национальным стандартом **ГОСТ Р 34.10-2012** («Процессы формирования и проверки электронной цифровой подписи», RFC 7091 / RFC 7836). Реализация выполнена на **чистом Python без внешних криптографических библиотек** (включая полное исключение зависимости от библиотеки `cryptography`).

Используется каноническая форма Вейерштрасса для эллиптических кривых над простым конечным полем $\mathbb{F}_p$:

$$y^2 \equiv x^3 + ax + b \pmod p$$

где $a, b \in \mathbb{F}_p$, а инвариант $4a^3 + 27b^2 \not\equiv 0 \pmod p$.

### Поддерживаемые параметры кривых:
1. **ГОСТ Р 34.10-2012 (512 бит) — основной режим**:
   * Набор параметров: `id-tc26-gost-3410-12-512-paramSetA` (OID: `1.2.643.7.1.2.1.2.1`, RFC 7836).
   * Порядок поля $p$: простое 512-битное число ($p = 2^{512} - 569$).
   * Порядок циклической подгруппы точек $q \approx 2^{512}$.
   * Базовая точка-генератор $P = (x_P, y_P)$ порядка $q$.
   * Спаренная хэш-функция: ГОСТ Р 34.11-2012 «Стрибог-512» (выход $l = 512$ бит, идеально покрывающий порядок группы $q$).
   * Длина подписи: 1024 бита (128 байт: 64 байта $R$ и 64 байта $S$).

2. **ГОСТ Р 34.10-2012 (256 бит)**:
   * Набор параметров: `id-tc26-gost-3410-2012-256-paramSetA` (CryptoPro-A, OID: `1.2.643.7.1.2.1.1.1`, RFC 7091 / RFC 4357).
   * Порядок поля $p = 2^{255} + 1073$, порядок циклической подгруппы $q \approx 2^{256}$.
   * Спаренная хэш-функция: ГОСТ Р 34.11-2012 «Стрибог-256» ($l = 256$ бит).
   * Длина подписи: 512 бит (64 байта: 32 байта $R$ и 32 байта $S$).

Ключевая пара:
* Секретный ключ подписи: случайное целое число $d \in_R [1, q - 1]$.
* Открытый ключ проверки подписи: точка кривой $Q = d \cdot P = (x_Q, y_Q)$.

Стойкость схемы базируется на алгоритмической неразрешимости задачи дискретного логарифмирования в группе точек эллиптической кривой (ECDLP).

---

## 5.2. Формирование и проверка подписи (Алгоритмы I и II ГОСТ Р 34.10-2012)

### Алгоритм формирования подписи (Алгоритм I, RFC 7091 §6.1):
1. Вычисляется криптографический хэш-код сообщения $M$ с помощью ГОСТ Р 34.11-2012:
   $$H = h(M)$$
2. Вычисляется целое число $\alpha$ по двоичному представлению вектора $H$, и определяется значение $e$:
   $$e = \alpha \bmod q \quad (\text{если } e = 0, \text{ то } e = 1)$$
3. Генерируется криптографически стойкое эфемерное случайное число $k \in_R [1, q - 1]$.
4. Вычисляется кратная точка кривой $C = k \cdot P = (x_C, y_C)$ и определяется:
   $$r = x_C \bmod q \quad (\text{если } r = 0, \text{ возврат к п. 3})$$
5. Вычисляется значение:
   $$s = (r \cdot d + k \cdot e) \bmod q \quad (\text{если } s = 0, \text{ возврат к п. 3})$$
6. Формируются двоичные векторы $R$ и $S$, соответствующие числам $r$ и $s$, и результирующая подпись формируется как их конкатенация:
   $$\zeta = (R \parallel S)$$
   (в сериализованном виде упаковывается в формат Base64).

### Алгоритм проверки подписи (Алгоритм II, RFC 7091 §6.2):
1. Из принятой подписи $\zeta$ извлекаются целые числа $r$ и $s$. Проверяется выполнение условий диапазона:
   $$0 < r < q \quad \text{и} \quad 0 < s < q$$
   (при нарушении подпись считается недействительной).
2. Проверяется корректность открытого ключа: $Q \neq \mathcal{O}$ и точка принадлежит кривой $y_Q^2 \equiv x_Q^3 + a x_Q + b \pmod p$.
3. Вычисляется хэш-код сообщения $H = h(M)$ и величина $e = \alpha \bmod q$ (если $e = 0$, то $e = 1$).
4. Вычисляется мультипликативно обратное значение в поле по модулю порядка подгруппы:
   $$v = e^{-1} \bmod q$$
5. Вычисляются линейные коэффициенты:
   $$z_1 = s \cdot v \bmod q, \quad z_2 = -r \cdot v \bmod q$$
6. Вычисляется точка эллиптической кривой:
   $$C = z_1 \cdot P + z_2 \cdot Q = (x_C, y_C)$$
7. Определяется значение $R = x_C \bmod q$. Цифровая подпись признается **подлинной** тогда и только тогда, когда:
   $$R = r$$

---

## 5.3. Структура самоподписанного сертификата пользователя

Для обеспечения неотказуемости авторства система CryptoMail автоматически генерирует для каждого пользователя самоподписанный цифровой сертификат, связывающий учетные данные пользователя с его открытым ключом ЭЦП ГОСТ:

```json
{
  "version": "1.0",
  "serial_number": "4B9A1E8F2C3D4E5F6A7B8C9D0E1F2A3B",
  "subject": {
    "common_name": "alexander",
    "user_id": 4,
    "organization": "CryptoMail Secure Network"
  },
  "issuer": {
    "common_name": "alexander (Self-Signed ЭЦП ГОСТ)",
    "user_id": 4
  },
  "valid_from": "2026-09-05T18:00:00Z",
  "valid_to": "2027-09-05T18:00:00Z",
  "signature_algorithm": "GOST-R-34.10-2012-512 + GOST-R-34.11-2012-Streebog-512",
  "public_key_pem": "-----BEGIN PUBLIC KEY-----\n...",
  "signature": "BB3RWUr8UW6lTaogMyku3GdMLijp8L/..."
}
```

Верификация сертификата осуществляется путем исключения поля `signature`, канонической сортировки JSON-ключей, вычисления дайджеста через «Стрибог-512» и проверки подписи открытым ключом, содержащимся в теле сертификата, по Алгоритму II ГОСТ Р 34.10-2012.

## 5.4. Отсоединенная ЭЦП в формате CMS / PKCS#7 SignedData (RFC 5652 / RFC 9215)

Для юридической значимости и совместимости с внешними системами (портал «Госуслуги», КриптоПро CSP, Контур.Диадок) отсоединенная электронная подпись (`.sig`) формируется не в виде «сырых» координат, а в виде полноценного криптографического контейнера **CMS (Cryptographic Message Syntax) / PKCS#7 SignedData** (ASN.1 DER) в соответствии с RFC 5652 и RFC 9215.

### Структура контейнера CMS SignedData:
1. **`ContentInfo`** (OID `1.2.840.113549.1.7.2` `id-signedData`):
   * Корневая последовательность SEQUENCE.
2. **`SignedData`**:
   * `version`: 1;
   * `digestAlgorithms`: `id-tc26-gost3411-12-512` (OID `1.2.643.7.1.1.2.3`, параметры опущены согласно RFC 9215);
   * `encapContentInfo`: `id-data` (OID `1.2.840.113549.1.7.1`), поле `eContent` опускается (так как подпись отсоединенная);
   * `certificates`: набор сертификатов `CertificateSet`, содержащий сертификат открытого ключа подписанта стандарта X.509 v3 (RFC 9215);
   * `signerInfos`: набор структур `SignerInfo`:
     * `sid`: идентификатор сертификата (IssuerAndSerialNumber);
     * `signedAttrs` (CAdES): подписанные атрибуты:
       - `contentType` (OID `1.2.840.113549.1.9.3` $\rightarrow$ `id-data`);
       - `messageDigest` (OID `1.2.840.113549.1.9.4` $\rightarrow$ хэш файла «Стрибог-512»);
       - `signingTime` (OID `1.2.840.113549.1.9.5` $\rightarrow$ время подписи UTCTime);
     * `signatureAlgorithm`: `id-tc26-signwithdigest-gost3410-12-512` (OID `1.2.643.7.1.1.3.3`);
     * `signature`: значение ЭЦП в представлении $S \parallel R$ (128 байт).

Благодаря корректной структуре ASN.1 DER контейнер `.sig` распознается Windows CryptoAPI (функции `CryptMsgOpenToDecode`, `CryptVerifyDetachedMessageSignature`) и государственными сервисами без ошибок `CRYPT_E_ASN1_BADTAG` (`0x8009310b`).

# Глава 6. Прозрачное шифрование базы данных (Database Encryption at Rest)

## 6.1. Модель угроз и архитектура защитного слоя

В случае компрометации физического сервера, несанкционированного создания дампов памяти или кражи файла базы данных `cryptomail.db` злоумышленник может получить доступ к учетным записям и переписке.
Для противодействия данной угрозе реализован модуль `crypto.db_cipher`, интегрированный непосредственно в модель данных SQLAlchemy.

## 6.2. Механизм прозрачной трансформации

Все конфиденциальные поля сущностей:
* Секретный ключ ЭЦП (`_ecp_private_key_enc`);
* Секретный ключ RSA (`_rsa_private_key_enc`);
* Резервные коды восстановления (`_recovery_codes`);
* Тема сообщения (`_subject_enc`);
* Тело шифротекста (`_ciphertext_enc`);
* Ключевой бандл (`_key_bundle_enc`)

экранируются симметричным шифром **ГОСТ Р 34.12-2015 «Кузнечик»** в режиме CBC с набивкой PKCS#7.

### Порядок преобразования при записи (Setter):
1. Исходные строковые данные кодируются в байты UTF-8.
2. Генерируется случайный 16-байтовый вектор инициализации $IV$.
3. Данные дополняются по стандарту PKCS#7 до кратности 16 байтам.
4. Выполняется шифрование блоками `kuznyechik.encrypt_cbc(data, iv=iv)`.
5. Шифротекст, содержащий префикс $IV$, кодируется в Base64 и сохраняется в столбце БД.

### Порядок преобразования при чтении (Getter):
1. Из столбца считывается строка Base64.
2. Декодируется в байтовую последовательность.
3. Первые 16 байт извлекаются как $IV$, оставшиеся блоки дешифруются через `kuznyechik.decrypt_cbc()`.
4. Снимается набивка PKCS#7, байты декодируются в строку UTF-8.

Мастер-ключ БД (`_DB_MASTER_KEY`) конфигурируется через переменную окружения `DB_MASTER_KEY_HEX` и никогда не хранится в открытом виде в самой базе данных.
